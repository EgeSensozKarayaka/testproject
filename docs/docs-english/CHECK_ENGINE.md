## 1. Purpose

This document finalizes the v1 contract of the scheduler-independent check engine that takes a check snapshot and produces a single HTTP observation. The engine:

- securely connects to the target;
- measures DNS, TCP, TLS, time to first byte (TTFB), and total duration;
- validates the expected status code and optional body text;
- deterministically classifies redirects, timeouts, IPv4/IPv6, oversized/infinite responses, and network errors;
- fails closed before establishing a connection in SSRF and DNS rebinding attempts;
- never propagates raw response body, URL query values, credentials, or target IP to persistent storage or logs;
- uses async streaming I/O where a single slow target does not block the Node.js event loop or other probes.

The engine is not an HTTP client wrapper. Security policy, time budgeting, bounded streaming, and error taxonomy are intrinsic parts of this domain component.

- Job creation, claim, lease, fencing, and overlap prevention for the same check: Stage 9
- Writing results to the `check_runs` table and rejecting stale snapshots: Stage 9
- `UP/SUSPECT/DOWN`, incident, and group status transitions: Stages 8–9

A crash or unexpected exception generated by the check engine does not signify that the target is down. Such an occurrence is a worker/job infrastructure fault and is not fed into the incident state machine as a target failure.

## 4. Architectural Boundaries

```text
CheckJob.config_snapshot
          |
          v
  Snapshot decoder/validator
          |
          v
      ProbeEngine
      |    |    |
      |    |    +--> MonotonicClock
      |    +-------> AddressPolicy
      +------------> ResolverPort
          |
          v
   Frozen public candidate set
          |
          v
     HttpTransport
   (direct, pinned I/O)
          |
          v
      ProbeResult
          |
          +--> Stage 9 persistence/fencing
          +--> Stage 8 state transition
```

`packages/check-engine` has no knowledge of databases, Fastify, schedulers, loggers, or environment variables. All runtime policy values and adapters are injected via the constructor. This ensures that the engine:

- is fully open to pure in-process integration testing;
- can run without a scheduler;
- can inject a policy in tests permitting only designated loopback origins;
- does not inadvertently inherit proxy or broad network access from within the application.

Because a direct, pinned low-level connection is required for the production adapter, rather than global `fetch`, a direct workspace-pinned `undici` dependency is utilized. Rather than writing a security-critical custom parser for IP/CIDR parsing, the pinned `ipaddr.js` library is used directly; the accepted blocks are managed via a repository-owned, tested policy table.

## 5. Input Contract

The engine is invoked solely with the immutable snapshot decoded by the worker from the job:

```ts
interface ProbeInputV1 {
  schemaVersion: 1;
  url: string;
  timeoutMs: number;
  expectedStatusCode: number;
  expectedBodySubstring: string | null;
}

interface ProbeInvocation {
  input: Readonly<ProbeInputV1>;
  signal: AbortSignal;
}
```

The snapshot contains no `owner_id`, check name, email, or loggable user text. The worker maintains correlation identifiers outside the engine.

Existing Stage 6 manual job snapshots do not carry a `schema_version`. In the Stage 7 implementation:

1. New jobs are written with snake_case `schema_version: 1`;
2. The decoder accepts only strictly recognized v1 fields;
3. During the migration transition, the exact legacy field set is normalized as version 1;
4. Missing, superfluous, type-incorrect, or unsupported versions are not considered target errors, but rather `UNSUPPORTED_JOB_SNAPSHOT` infrastructure faults;
5. Snapshot contents are not logged.

Even though the URL was previously validated at the API layer, it is validated again at the worker trust boundary. Persistent data is not treated as trusted input.

## 6. Output and Error Contract

### 6.1 Target Result

```ts
type ProbeFailureCategory =
  | 'DNS_ERROR'
  | 'CONNECT_ERROR'
  | 'TLS_ERROR'
  | 'TIMEOUT'
  | 'TOO_MANY_REDIRECTS'
  | 'BLOCKED_TARGET'
  | 'RESPONSE_TOO_LARGE'
  | 'UNEXPECTED_STATUS'
  | 'BODY_MISMATCH'
  | 'PROTOCOL_ERROR'
  | 'UNKNOWN_NETWORK_ERROR';

interface ProbeTimings {
  dnsMs: number | null;
  connectMs: number | null;
  tlsMs: number | null;
  ttfbMs: number | null;
  totalMs: number;
}

interface ProbeResult {
  outcome: 'PASS' | 'FAIL';
  failureCategory: ProbeFailureCategory | null;
  statusCode: number | null;
  bodyMatch: boolean | null;
  timings: ProbeTimings;
  redirectCount: number;
  diagnosticCode: ProbeDiagnosticCode | null;
}
```

`diagnosticCode` is not free-form text; it is a fixed allowlist enum. If necessary, a brief, non-sensitive description of this stable code is written to the database `diagnostic` field. Socket error messages, stack traces, URLs, IPs, DNS answers, `Location` headers, or response bodies never enter this field.

Semantics of `bodyMatch`:

- `null` if there is no expectation;
- `true` if an expectation exists and was found within the stream following status verification;
- `false` if the stream completed without finding the substring;
- `null` if a network, status, or size error occurred prior to evaluating the body.

### 6.2 Infrastructure Result

The following are not `ProbeResult FAIL`; they return to the caller as typed exceptions/faults:

- Caller signal indicating lost lease, shutdown, or job cancellation;
- Corrupted/unsupported snapshot;
- Engine invariant violation;
- Adapter/programming error.

The worker does not treat these as target runs or incidents; it routes them according to job retry/dead-letter and observability policies. Expiration of the global probe deadline, on the other hand, constitutes a `TIMEOUT` outcome with respect to the target.

## 7. Single Probe Algorithm

1. The monotonic start time is captured; `deadline = start + timeoutMs` is computed.
2. Snapshot fields and canonical URL are re-validated.
3. For the initial hop, scheme, userinfo, hostname, port, URL length, and fragment policies are applied.
4. If the host is an IP literal, it is passed directly to the address policy; if it is a hostname, it is passed to the resolver.
5. **All** A/AAAA candidate records returned by the resolver are normalized and validated.
6. If even a single candidate is blocked, invalid, has a zone ID, or is a mapped-private address, the entire hop becomes `BLOCKED_TARGET`; no connection attempt is made.
7. The validated candidate set is passed immutably to the transport connector. The connector cannot perform DNS lookups.
8. TCP and (if required) TLS connections are established within the remaining total budget; Host and SNI are set to the original canonical hostname.
9. A minimal GET request is dispatched; headers and body are received via bounded streaming.
10. If the response is a redirect, `Location` is resolved, policies are re-applied from the beginning, and a new short-lived client is instantiated.
11. On the final response, size, status, and optional body expectations are evaluated in deterministic order.
12. When the stream completes via EOF or error, total duration is measured and the typed result is returned.
13. In all cases, sockets/clients, decoders, and timers are closed within a `finally` block.

The engine does not perform retries. Scheduler retries are also not executed immediately for normal target failures; recurrences follow the user-configured interval cadence. This prevents a probe from inflating timeouts and target load through hidden repeated attempts.

## 8. URL and Request Policy

### 8.1 URL Validation

- The WHATWG `URL` parser is used.
- Only `http:` and `https:` schemes are accepted.
- URLs containing a username or password are rejected.
- Hostname is mandatory; IPv6 zone IDs are rejected.
- Fragments are stripped from the request; query parameters are transmitted to the target but are never written to any telemetry, log, or result fields.
- Canonical URL UTF-8 byte length is capped at 2048; URLs following a redirect are subject to the same constraint.
- Internationalized domain names are resolved after being converted by WHATWG into ASCII/Punycode canonical hostnames.
- The default HTTP port is 80; default HTTPS port is 443.
- The port must reside within an operator-controlled allowlist. The production default is `80,443`; expansion is performed via deployment configuration, never via user requests.
- `localhost`, `.localhost`, `.local`, `.internal`, `.home.arpa`, and single-label internal domain names are blocked prior to DNS resolution. This list does not substitute for IP validation.

### 8.2 Request

- Method is exclusively `GET`.
- No request body is sent, including during redirects.
- `Host` and TLS SNI are derived from the canonical URL host; they are not replaced with the pinned IP.
- Stable `User-Agent`, `Accept: */*`, `Accept-Encoding: identity`, and `Cache-Control: no-cache` headers are sent.
- No cookie jar, Authorization, Proxy-Authorization, Referer, custom headers, or ambient credentials are used.
- Runtime environment variables `HTTP_PROXY`, `HTTPS_PROXY`, `ALL_PROXY`, and `NO_PROXY` are ignored; connections are direct.
- HTTP upgrade (`101`) and CONNECT tunneling behaviors are not supported.
- HTTP/1.1 is the mandatory v1 baseline; HTTP/2 optimization can only be enabled via a separate architectural decision record after passing identical pinning, timing, and boundary tests.

## 9. DNS, IP Policy, and Rebinding Defense

### 9.1 Resolver

The production resolver adapter uses an isolated `node:dns` Promise `Resolver` for each hop, querying both A and AAAA records. It does not silently trust operating system hosts file or search-domain behaviors. Upon external abort or deadline expiration, the resolver is cancelled; late results are discarded.

- For IP literals, DNS resolution is skipped and `dnsMs = 0`.
- The final A/AAAA records of CNAME chains are validated.
- If there are no responses or all queries produce appropriate DNS errors, the outcome is `DNS_ERROR`.
- A maximum of 16 addresses are accepted. Exceeding this limit results in a fail-closed `DNS_ERROR/DNS_RESPONSE_LIMIT`; answers are not truncated to continue for security reasons.
- Duplicate addresses are deduplicated in canonical byte form.
- Resolver ordering is not the sole source of truth for IPv4/IPv6 preference; the transport may only perform bounded family selection within the verified candidate set.

### 9.2 Public Address Rule

The policy does not merely block a handful of private CIDRs through a simplistic denylist approach. An address:

- must be canonical IPv4 or IPv6;
- if it is an IPv4-mapped IPv6 address, it must first be normalized to the embedded IPv4 address and evaluated against the same rules;
- must not carry zone or scope identifiers;
- must not belong to loopback, unspecified, private, link-local, multicast, broadcast, carrier-grade NAT, benchmark, documentation, protocol-assignment, reserved, or future-use blocks;
- cloud metadata addresses and specialized service endpoints must be explicitly blocked;
- must not belong to any block marked `Globally Reachable = False` in the IANA special-purpose registries.

Standard global unicast addresses are accepted. A reviewed CIDR table is maintained in the repository; policy data is never downloaded from IANA during application runtime. Updating the table requires a security review and unit testing.

If a hostname resolves to both public and blocked addresses, the entire hop is blocked rather than selecting only the public address. This prevents an attacker from intermittently reaching a private target via round-robin or dual-stack DNS responses.

### 9.3 Pinning

The most critical invariant:

> The address set observed during security validation for a hop is identical to the address set to which the socket connects.

Flow:

1. The hostname is resolved once;
2. All answers are validated;
3. A canonical, immutable candidate set is constructed;
4. The Undici custom connector/lookup callback returns only this set;
5. The callback cannot make new DNS queries;
6. A new redirect hop performs resolution and validation anew from scratch;
7. The per-hop client is closed upon conclusion of the single request; it never shares a connection pool with other jobs or subsequent DNS evaluations.

TLS certificate and hostname validation is performed against the original hostname, not against the IP address. `rejectUnauthorized` cannot be disabled; custom CAs and insecure modes are not supported in v1.

A short-lived per-hop client introduces additional handshake overhead compared to a global keep-alive connection pool; in return, it keeps the boundary against stale DNS and connection pool rebinding simple and verifiable. A more complex `(scheme, host, port, validated-address-set)` connection pool will not be introduced without profiling under 20/200/500 load.

### 9.4 Narrow Development Exception for Simulator

The actual product does not target private networks; however, `target-simulator` inside Docker naturally uses private IP addresses. This contradiction is not resolved via a blanket `ALLOW_PRIVATE_NETWORKS=true` flag.

- In tests, `AddressPolicy` is injected via an adapter permitting solely the fixture's exact loopback address/origin.
- In local Compose demos, an exact canonical origin allowlist may be utilized strictly when `NODE_ENV=development`.
- Local Compose additionally adds the simulator's port `4010` to the deployment port allowlist; the private-address exception does not implicitly bypass the port policy.
- The exception is tied to a scheme + hostname + port triplet and does not accept wildcards or CIDRs.
- Any different origin redirected from an allowed origin remains subject to standard public policy.
- In production configuration, if this field is non-empty, the process fails fast on startup.
- This exception cannot be modified via external APIs or on a per-user basis.

## 10. Redirect Policy

- Only `301`, `302`, `303`, `307`, and `308` with a valid `Location` header are followed as redirects.
- `Location` can be relative; it is resolved relative to the current URL using WHATWG.
- A maximum of 5 redirects are followed. The sixth results in `TOO_MANY_REDIRECTS`.
- Encountering an identical canonical URL again immediately triggers `TOO_MANY_REDIRECTS/REDIRECT_LOOP` without waiting for the limit to be reached.
- Every hop undergoes scheme, userinfo, hostname, port, DNS, all-IP, and pinning validation.
- An HTTPS → HTTP downgrade results in `BLOCKED_TARGET/REDIRECT_DOWNGRADE`. HTTP → HTTPS upgrades are permitted.
- Credentials, custom headers, or cookies are not propagated across redirects; the engine does not support these anyway.
- If `Location` is missing or unparseable, but that status code is the expected status, it may be evaluated as the final response; an attempted but invalid `Location` header yields `PROTOCOL_ERROR`.
- Final status and body expectations are applied exclusively to the final response.
- Response bodies of redirect hops are not read; the response is safely aborted and the per-hop client is closed.

`redirectCount` represents the number of hops actually followed. Hostnames or URLs within the redirect chain are never written to results or logs.

## 11. Timeout, Deadline, and Cancellation

The user's `timeoutMs` value constitutes the single, definitive **total probe budget**. It encompasses the entirety of:

- URL and policy evaluation;
- DNS resolution;
- All address connection attempts;
- TCP and TLS handshakes;
- The redirect chain;
- Response headers and TTFB;
- Bounded reading and decoding of the body until EOF.

Every downstream layer utilizes the remaining budget. Individual runtime limits may only be narrower:

| Limit               |      Default | Rule                                          |
| ------------------- | -----------: | --------------------------------------------- |
| Total probe         | job snapshot | Canonical deadline                            |
| Connect+TLS per hop |    10,000 ms | `min(remaining, configured maximum)`          |
| Response headers    |    remaining | No separate long default may be used          |
| Body idle           |    remaining | Each chunk does not extend the total deadline |
| Redirect            |            5 | Does not reset the time budget                |

The timer does not grant a renewed total duration for each hop. The deadline begins once and remains identical throughout redirects and IPv4/IPv6 fallback attempts.

- If the global deadline expires, the target outcome is `TIMEOUT` regardless of the underlying lower-level error.
- If caller `AbortSignal` fires first, a typed `CANCELLED` infrastructure outcome is produced; target `TIMEOUT` is not recorded.
- Races between deadline expiration and caller abort are resolved deterministically via monotonic deadline checks.
- Timer, socket, DNS, and decoder cleanup must be idempotent.
- `setTimeout` is not used in isolation; actual I/O is aborted via AbortSignal or socket destroy.

## 12. Timing Measurements

Durations are measured using a monotonic clock similar to `performance.now()`; `Date.now()` is reserved solely for the worker's wall-clock `started_at/finished_at` fields.

| Field       | Meaning                                                                                    |
| ----------- | ------------------------------------------------------------------------------------------ |
| `dnsMs`     | Name resolution time; `0` for IP literals; `null` for URLs blocked before DNS begins       |
| `connectMs` | TCP connection time; elapsed connect time may also be measured if connection fails         |
| `tlsMs`     | Post-TCP TLS handshake; measured only on HTTPS hops, otherwise `null`                      |
| `ttfbMs`    | Elapsed time between request dispatch and the start of response headers                    |
| `totalMs`   | Total duration from initial engine invocation to body EOF, error, or cancellation decision |

When redirects occur, phase fields represent the sum of the respective durations across all hops; `totalMs` reflects the wall duration of the entire chain. The sum of individual phases is not expected to exactly equal `totalMs`, as URL parsing, stream reading, decoding, and scheduling gaps also contribute.

Durations are rounded to non-negative integer milliseconds. Phases that never commenced are `null`, while phases that commenced but fell below measurement resolution may be `0`. Measurement instrumentation does not include exception messages or IP addresses.

## 13. Response Reading and Body Validation

### 13.1 Header and Body Limits

- Total header size is capped at 16 KiB; exceeding this results in `PROTOCOL_ERROR/HEADERS_TOO_LARGE`.
- Hard caps of 1 MiB are enforced separately for wire body and decoded body.
- If `Content-Length` is valid and exceeds the cap, `RESPONSE_TOO_LARGE` is returned without reading the stream.
- In chunked or length-less responses, the socket is aborted the instant the byte counter exceeds the cap.
- The body is never accumulated in memory, never written to disk, and never supplied to any callback, log, or event.
- Status-only checks also consume the bounded stream until EOF; this ensures total duration measures true completion and prevents infinite bodies from hanging without timing out.

`Accept-Encoding: identity` is transmitted. If the server nevertheless returns compressed content:

- If no body expectation exists, the wire stream is consumed in a bounded fashion;
- If a body expectation exists, it is decompressed using a single Node stream decoder for `gzip`, `deflate`, or `br`;
- Both wire and decompressed byte caps remain enforced;
- Unknown or multiple content-encodings result in `PROTOCOL_ERROR/UNSUPPORTED_CONTENT_ENCODING`.

### 13.2 Streaming Substring

The expected body is bounded at the API boundary to 1–2048 UTF-8 bytes. The engine converts this to a UTF-8 byte pattern and uses a streaming matcher operating across chunk boundaries. Only the matcher state and a bounded overlap proportional to the pattern size are maintained in memory.

- Exact byte-level, case-sensitive matching is used.
- No HTML parsing, Unicode normalization, regular expressions, or character set transcoding are performed.
- Even if a match is discovered early, the stream is consumed until EOF within the size cap and deadline.
- An invalid UTF-8 response that does not contain the target byte pattern is treated as a normal mismatch; the body is not logged.

### 13.3 Evaluation Precedence

Deterministic order of precedence:

1. Caller cancellation — infrastructure outcome
2. Total deadline — `TIMEOUT`
3. URL/address/redirect security — `BLOCKED_TARGET`
4. DNS/connect/TLS/protocol/network failure
5. Redirect loop/limit
6. Header/body/decompressed size — `RESPONSE_TOO_LARGE` or protocol error
7. Expected status — `UNEXPECTED_STATUS`
8. Expected body — `BODY_MISMATCH`
9. `PASS`

This order is tested. For instance, if the status code differs from expected but `Content-Length` is 2 GiB, `RESPONSE_TOO_LARGE` takes precedence for resource protection; if the deadline expires while reading the body, the outcome is `TIMEOUT`, not `BODY_MISMATCH`.

## 14. Error Taxonomy

| Category                | Examples                                                                             |      Status Present? | Retryable Flagging         |
| ----------------------- | ------------------------------------------------------------------------------------ | -------------------: | -------------------------- |
| `DNS_ERROR`             | NXDOMAIN, SERVFAIL, no response, too many addresses                                  |                   No | On next cadence            |
| `CONNECT_ERROR`         | Connection refused, unreachable, all validated candidates failed                     |                   No | On next cadence            |
| `TLS_ERROR`             | Certificate error, hostname mismatch, handshake failure, unsupported secure protocol |                   No | On next cadence            |
| `TIMEOUT`               | Total deadline expired during DNS, connect, header, or body                          |            Sometimes | On next cadence            |
| `TOO_MANY_REDIRECTS`    | Limit exceeded or redirect loop detected                                             | May be last redirect | Config/target needs fixing |
| `BLOCKED_TARGET`        | Private/special IP, unsafe port, protocol downgrade, mixed DNS                       |                   No | Policy/config needs fixing |
| `RESPONSE_TOO_LARGE`    | Content-Length, wire, or decoded cap exceeded                                        |                  Yes | Target/config needs fixing |
| `UNEXPECTED_STATUS`     | Final status does not match expected status                                          |                  Yes | On next cadence            |
| `BODY_MISMATCH`         | Substring not found at EOF                                                           |                  Yes | On next cadence            |
| `PROTOCOL_ERROR`        | Malformed HTTP, oversized headers, unsupported encoding/upgrade                      |            Sometimes | On next cadence            |
| `UNKNOWN_NETWORK_ERROR` | Socket/network error outside audited safe mapping                                    |            Sometimes | On next cadence            |

Raw Node/Undici error codes are not part of the external contract. The adapter uses an audited mapping table. Unknown network exceptions become `UNKNOWN_NETWORK_ERROR`; programming/invariant exceptions represent engine faults. This prevents genuine code bugs from masquerading as target downtime.

Example diagnostic codes: `DNS_NXDOMAIN`, `DNS_SERVFAIL`, `DNS_RESPONSE_LIMIT`, `CONNECT_REFUSED`, `TLS_CERTIFICATE`, `TOTAL_DEADLINE`, `PRIVATE_ADDRESS`, `MIXED_ADDRESS_SET`, `PORT_NOT_ALLOWED`, `REDIRECT_LOOP`, `REDIRECT_DOWNGRADE`, `WIRE_BODY_LIMIT`, `DECODED_BODY_LIMIT`, `STATUS_MISMATCH`, `EXPECTED_TEXT_MISSING`.

## 15. Privacy and Observability Boundary

### 15.1 Allowed Fields to Log

- Worker/service version
- Job/check ID — from worker context
- Result category and diagnostic enum
- Numeric timings, redirect count, and response status
- Result outcome

### 15.2 Forbidden Fields

- Full/canonical URL and query parameters
- Response body or body preview/hash
- Expected substring
- DNS answers, selected IP, or redirect `Location`
- Request/response header values
- Cookies, credentials, tokens, stack traces / exception messages

High-cardinality hostname metric labels are forbidden. If necessary, the worker may use only a short host bucket hashed via a process-secret HMAC in metrics; this is a Stage 17 decision.

The logger is not a dependency of the engine. The worker extracts allowlisted fields from the typed result. Serializing error objects directly via `{ err }` is forbidden; the adapter returns only safe diagnostic enums.

Negative tests search memory log sinks, returned results, metric labels, and serialized diagnostics for query secrets, expected text markers, and body markers.

## 17. Target Simulator

`apps/target-simulator` mimics internet targets; it does not mimic security policies. Endpoints must be deterministic and bounded:

| Endpoint                        | Behavior                                                       |
| ------------------------------- | -------------------------------------------------------------- |
| `GET /ok`                       | `200`, static expected content                                 |
| `GET /status/:code`             | Requested valid HTTP status                                    |
| `GET /delay/:milliseconds`      | Bounded delay before headers                                   |
| `GET /stream/:chunks/:delay`    | Bounded body with delay between chunks                         |
| `GET /hang`                     | No response until client terminates connection                 |
| `GET /body/match` / `mismatch`  | Expected text fixture spanning chunk boundaries                |
| `GET /large/:bytes`             | Streaming large body without buffering single buffer in memory |
| `GET /compressed/:encoding`     | gzip/deflate/br body                                           |
| `GET /redirect/:remaining`      | Relative redirect chain terminating at `/ok`                   |
| `GET /redirect-loop/a` and `/b` | Deterministic loop                                             |
| `GET /redirect-to?target=`      | Test-only validation for private/unsafe redirects              |
| `GET /flaky/:key`               | Configured 503/200 sequence on isolated fixture instance       |
| `GET /close`                    | Closes socket prior to completing response                     |

The simulator does not log query or body values. All parameters have upper limits; the fixture cannot cause memory or connection DoS on its own. Flaky state is a process-local test fixture, not product state; parallel tests use separate instances or keys.

For TLS scenarios, the test suite uses an ephemeral HTTPS server and a test-only self-signed certificate. Private keys never enter production images or configuration. Existing health endpoints of the simulator are preserved.

## 18. Test Strategy

### 18.1 Unit Tests

- URL canonicalization, userinfo, scheme, port, hostname, and redirect downgrade
- Canonical IPv4/IPv6 parsing; mapped IPv4, zone IDs, and all blocked CIDR boundaries
- Boundary addresses of the IANA policy table
- Complete rejection of mixed public/private DNS result sets
- Streaming matcher across all possible chunk boundaries
- Wire and decoded byte counters and exact cap boundaries
- Error mapping and precedence table
- Races between monotonic deadlines and aborts using fake clocks
- Legacy/v1 snapshot decoder and rejection of unknown fields/versions

### 18.2 Real I/O Integration Tests

- HTTP success, unexpected status, body match/mismatch
- IPv4 and (if supported by environment) IPv6 loopback
- TLS success with test CA, expired / wrong-host / self-signed failures
- Connect refused, socket close, malformed HTTP
- Header delay, body delay, and infinite hang timeouts
- Redirects: relative, cross-host, loop, limit, downgrade, private target
- Oversized Content-Length, chunked wire body, and decompression bombs
- Verification that caller cancellation does not produce target failure
- Closure of all resources upon test conclusion

Test policies accept only the exact loopback origin of the created fixture; production private-address policies are never relaxed.

### 18.3 SSRF and Rebinding Proofs

- Literal `127.0.0.1`, `::1`, RFC1918, link-local, CGNAT, multicast, documentation, and metadata addresses
- URL parser variations such as decimal, octal, and hex following canonical form
- IPv4-mapped IPv6 private addresses
- DNS responses with only private and mixed public/private answers
- Resolver returning public on first call and private on a hypothetical second call: resolver call count is 1 and connector observes only the frozen initial set
- Redirect from public origin to private target: private connector is never invoked
- Escaping dev exact-origin exceptions via different port, host, or redirect
- Tests proving ambient proxy environments do not alter connection routing

### 18.4 Concurrency and Resource Tests

- At least 50 engine invocations within the same process; rapid invocations complete independently alongside a hanging request
- In scenarios where all requests time out, active socket, timer, and decoder counts return to baseline
- Under large responses, heap does not scale linearly with body size
- Relaxed regression threshold for event-loop delay

Testing 20/200/500 checks and fairness is the completion gate for the Stage 9 scheduler, not the engine. Stage 7 proves the non-blocking primitives that make this scale possible.

### 18.5 Property / Fuzz Tests

- IP textual formatting and CIDR boundaries
- Redirect URL resolution and loop canonicalization
- Arbitrary chunk slicing of expected substrings
- Event sequences for error precedence

Fuzz tests perform no network access and output fixed seeds upon failure.

## 19. Performance and Capacity Model

A balanced distribution of 500 checks with a 30-second interval translates to an average of approximately 16.7 probes/s; this figure is not a product limit. The engine's capacity principles:

- Socket, DNS, and body operations are entirely asynchronous;
- O(1) body memory per probe, with matcher state bounded by expected pattern size;
- Bounded network and CPU utilization enforced via response and redirect limits;
- Zero cross-job connection state sharing due to per-hop clients;
- No synchronous DNS, synchronous cryptography, full-body buffering, or unbounded Promise fan-out.

Global, owner, and hostname semaphores, jitter, and fairness reside in the scheduler/worker layer. Creating a global queue inside the engine is avoided because it would obscure scheduler visibility. If handshake overhead fails to meet targets during Stage 9 load testing, a safe pool constrained by validated candidate-set identity, TTL, and maximum lifetime will be evaluated via a separate ADR.

## 20. Resilience and Lifecycle

- The engine is stateless; persistence across server restarts resides in the job and check database tables.
- If a probe process is killed, partial target runs are not recorded; lease expiry and reclamation are handled in Stage 9.
- Deadline/cancellation cleanup is idempotent and callable multiple times.
- Late callbacks from resolvers, connectors, or decoders cannot alter completed outcomes.
- A single invocation produces exactly one terminal result.
- The engine produces no process-level `unhandledRejection`.
- Engine faults are not converted to target failures; worker readiness is affected only if the systemic fault rate exceeds designated thresholds.

## 21. Implementation Slices

1. Public types, snapshot decoder, policy configuration, and diagnostic enum
2. Strict URL/IP/CIDR policy and comprehensive boundary tests
3. Resolver adapter, frozen candidate set, and rebinding test double
4. Undici pinned transport, lifecycle, and phase instrumentation
5. Total deadline/cancellation and deterministic error mapping
6. Bounded streaming, compression, and substring matcher
7. Redirect state machine
8. Target simulator endpoints and real I/O integration suite
9. Monitor-worker standalone probe composition wiring only; no scheduler claim or persistence
10. Leak, concurrency, redaction, and CI completion tests

Each slice passes `format`, `lint`, strict `typecheck`, unit, and relevant integration tests. Dependency lockfiles, licenses, and security audit outputs are also reviewed.

## 22. Completion Gate

Stage 7 is complete only when all of the following criteria are satisfied:

- `ProbeEngine` executes deterministically without a scheduler or database.
- HTTP/HTTPS success, status/body mismatch, and all network failure categories are thoroughly tested.
- Global deadlines reliably abort I/O across DNS, headers, body, and hangs.
- Every redirect hop undergoes re-resolution and full policy validation.
- In rebinding tests, sockets connect exclusively to the validated frozen candidate set.
- On private, special-use, or mixed DNS responses, the connector is never invoked.
- Memory consumption for body and headers remains bounded; raw response bodies never reach any output.
- Slow or hanging probes do not block other fast probes.
- Caller cancellation does not produce target failures.
- The simulator provides all required deterministic scenarios.
- The full repository quality gate and container smoke tests pass.
- `DECISIONS`, `DEVELOPMENT_LOG`, and `PROJECT_STATUS` are updated with verified outcomes.

## 23. Known Trade-offs

- Short-lived per-hop connections forfeit keep-alive performance benefits in exchange for simplifying security proofs.
- The default 80/443 port allowlist blocks certain legitimate custom ports without explicit operator configuration.
- Byte-level UTF-8 substring semantics omit charset and DOM awareness to remain deterministic and bounded.
- The HTTP/1.1 baseline excludes h2-only targets.
- The public-only policy intentionally omits intranet monitoring use cases.
- Stage 7 secures single-probe execution; guarantees regarding overlapping runs of the same check and aggregate concurrency are not product acceptance criteria until Stage 9 is complete.
