## Known Limitations

- The public page uses 10-second polling instead of real-time SSE; it fulfills the requirement of refreshless updates specified in the task but does not provide an instantaneous push guarantee.
- Production worker loop, 20/200/500 runtime throughput/queue-lag, natural lease reclaim / stale-result fencing after SIGKILL, and API latency under load with two real workers have been verified. Measurements serve as a local regression baseline; they are not production SLOs or multi-node PostgreSQL/network partition guarantees.
- Auth rate limit uses a PostgreSQL fixed-window approach. It is consistent for V1 and horizontal API replicas; high-volume internet traffic requires an edge WAF/CDN layer.
- For local Compose convenience, a single PostgreSQL bootstrap login assumes narrow `NOLOGIN` roles. Production requires dedicated login wrappers/secrets per service.
- In the local HTTP environment, session cookie is `Secure=false`; production config requires fail-fast secrets and HTTPS/Secure cookies.
- Auth security audit events record basic mutations; granular deny/metric/export coverage will be expanded in Stage 17 observability hardening.
- Housekeeping retention runs automatically; it applies a 24-hour detach grace period before permanently dropping a partition. Production legal hold/archive policy and managed restore drill are not yet established.
- Local restore rehearsal does not constitute a production RPO/RTO/PITR guarantee.
- Cold Docker image builds depend on registry network speed; shared BuildKit pnpm cache and low network concurrency have been applied; warm builds and normal `up` flows are faster.
- The last local clean image build attempt could not complete due to `ECONNRESET/error 23` interruptions from the external npm registry. Persistent pnpm cache, lower concurrency, and increased retries were added to Dockerfiles; the running stack was updated with verified host build outputs. GitHub `container-smoke` clean build results provide the final remote proof prior to delivery.
- Because host ports `5432` and `3000` are used by other projects, PostgreSQL is on port `15432`, API on `13000`, and web on `15173`.
- The list page loads 100 records per page by user request. 20/200/500 API profiles and the 500-record bounded UI fixture passed; manually opening all pages in a browser to generate a much larger DOM does not utilize virtualization.
- Group cursor currently uses a single active HMAC key; a key-ring accepting the previous verification key for seamless key rotation should be added in Stage 17 hardening.
