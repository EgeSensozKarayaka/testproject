# AI Usage

**Last Updated:** 2026-10-10 19:35 +06:00

## Tools and Model

The project is developed using a coding agent from the OpenAI GPT-5 family within the Codex desktop environment. Codex was selected for its capability to inspect and edit repository files, execute terminal commands, run test suites, manage Git workflows, and verify GitHub Actions results. Handling code, tests, and documentation in a unified workspace makes it straightforward to correlate architectural decisions directly with implemented runtime outcomes.

## Operating Model

- The human developer directs product requirements, scope boundaries, and stage approvals.
- The AI agent evaluates options, drafts architecture specifications, implements code, runs test suites, and reports outcomes.
- Critical architectural choices are recorded with timestamps in `docs/DECISIONS.md`; development steps in `docs/DEVELOPMENT_LOG.md`; verified and remaining scope in `docs/PROJECT_STATUS.md`.
- Canonical requirements reside in `AGENTS.md`, `docs/REQUIREMENTS.md`, and `docs/ACCEPTANCE_CRITERIA.md`. AI proposals are continuously validated against these sources and automated test executions.
- Prompts and session transcripts can be included upon delivery; this document provides a substantive summary of prompts and design decisions without leaking secrets or personal data.

## Key Prompts and Decisions Summary

1. The project was requested to meet enterprise-grade engineering standards without premature microservice fragmentation; a modular monolith paired with an isolated, failure-decoupled Python predictor was selected.
2. True multi-tenant user ownership was requested; organization/team tenancy was deliberately excluded from v1.
3. Persistence, API contracts, and authentication were split into discrete milestones: architecture document first, followed by implementation and automated verification gates.
4. Stage 5 implemented opaque sessions, Argon2id hashing, CSRF/origin protection, PostgreSQL rate limiting, encrypted durable auth emails, and Mailpit verification.
5. A notifier schema permission omission uncovered on a clean database during development was resolved cleanly via a new forward-only migration rather than mutating past migrations.
6. In Stage 6, check/group capabilities were first specified in an architecture document; implementation was broken into domain/migration foundations, followed by authenticated group APIs with atomic commits and real PostgreSQL integration tests.
7. Group route tests exposed an OpenAPI-to-Fastify path parameter mismatch (`{param}` vs `:param`); the AI fixed this within the type generator, verified via contract drift tests and real UUID route assertions.
8. In Stage 8, the approved health/incident architecture was translated into a pure TypeScript state reducer. The AI authored unit sequences and regression suites covering acceptance precedence, two-failure threshold, provisional interval resolution, gap accounting, and read-time freshness; all verified with strict type checking and real PostgreSQL.
9. During Stage 9 scheduler/worker design, the AI analyzed lock hierarchies and cancellation boundaries across migrations, API commands, probe engine, and health reducer. This led to a check-first canonical locking order, durable cancellation acknowledgement for in-flight jobs, and coalesced manual intents that preserve execution mode. Implementation was held until explicit user approval.
10. In Stage 9 Slice 1, the AI implemented Revision 14, typed worker configurations, and a shared activation-aware outbox writer. Real PostgreSQL tests caught an unnecessary `SELECT` permission demanded by `INSERT ... RETURNING` on the API role; rather than broadening role permissions, the helper was corrected to operate strictly within existing narrow `INSERT` grants.
11. In Stage 9 Slice 2, the AI implemented fixed-cadence calculation, deterministic exponential backoff helpers, and the check-first PostgreSQL job queue adapter. Fair candidate selection was computed before global limits via SQL window functions; worker race handling, attempt lineage, monotonic fencing tokens, and conditional start/heartbeat were proven on real PostgreSQL.
12. In Stage 9 Slice 3, the AI implemented the probe dispatcher featuring process-secret HMAC concurrency slots, bounded global/owner/host concurrency, an active task registry, strict snapshot decoding, lease heartbeat/cancellation aborts, and typed result/fault sinks. Because an atomic result sink was not yet in place, the production polling loop was intentionally kept idle to prevent orphaned `RUNNING` jobs.
13. In Stage 9 Slice 4, the AI implemented cancellation acknowledgements, typed infrastructure retries (`DEAD` states), and owner-fair expired-lease reclamation following the strict `check -> job -> attempt` lock order. PostgreSQL tests revealed that driver timestamp precision rounding broke manual intent cleanup checks; with row locks already held, fragile timestamp comparisons were removed, ensuring coalesced intents materialize atomically with terminal transitions.
14. In Stage 9 Slice 5, the AI built the atomic observation adapter linking probe outputs to the pure state reducer. Concurrent duplicate writers, manual intent materialization, PASS/FAIL incident transitions, diagnostic and cancellation rejection, rollback guarantees, and payload redaction were validated on PostgreSQL. Monotonic run timestamps derived from DB clock and locked lineage prevented zero-length interval artifacts during rapid executions.
15. In Stage 9 Slice 6, the AI wired owner-fair deadline candidate queries and the check-first freshness reconciler to the observation pipeline. Dual-replica idempotency, exact-deadline incident suspension, and lock-order contention were proven on PostgreSQL without requiring new migrations or dependencies.
16. In Stage 9 Slice 7, the AI connected the four runtime polling loops to the production entrypoint, adding loop-aware readiness, UTC partition preflights, and bounded graceful shutdown. Live Compose smoke testing revealed subtle microsecond equality issues and exact-allowlist Docker hostname ordering that unit tests missed; both were fixed with targeted regression suites. Real run continuity across restarts, `PASS/200`, `UP/FRESH`, zero duplicate jobs, and clean SIGTERM drains were verified.
17. In Stage 9 Slice 8, the AI authored a real PostgreSQL capacity test suite exercising 20, 200, and 500 due checks across the production queue, dispatcher, and persistence pipelines. External network variability was isolated with a deterministic 5/50 ms mock probe port, while Stage 7's 50-socket integration tests provided complementary proof. Throughput, memory, connection pools, and latency metrics were recorded machine-readably.
18. In Stage 9 Slice 9, the AI validated failure recovery by terminating the monitor entrypoint child process during an active hanging probe. Natural lease expiry, higher-fence replacement execution, and the rejection of stale late results as harmless non-mutating history were verified on PostgreSQL. Distinct failure semantics between crashes and zombie deliveries were formally documented.
19. At Stage 9 closing, the AI ran two production monitor workers and the API entrypoint across three processes on an isolated PostgreSQL instance. Exact parity of 200 checks across jobs, attempts, runs, and probe targets was proven while API list and readiness latency was benchmarked under load.
20. In Stage 10 Slice 1, the AI reconciled an OpenAPI `note` vs database `name` naming conflict using forward-only Revision 15, while revoking physical maintenance deletion and target update privileges. A security-invoker projection function was created to enforce uniform half-open `[start, end)` maintenance checks across API, monitor, and notifier components.
21. In Stage 10 Slice 2, the AI built owner-scoped maintenance CRUD services, routes, time-filtered OpenAPI contracts, and configurable quota enforcement. To maintain strict exact idempotency contracts, replay responses return original receipts rather than dynamically re-evaluating time-dependent states. Time-dependent evaluations within mutations use post-lock DB clocks.
22. In Stage 10 Slice 3, the AI evaluated check/group transaction boundaries alongside maintenance creation and cancellation races. A shared effect helper cleanly cancelled non-finalized maintenance windows upon check/group deletion without requiring auxiliary job tables. Events were dispatched to notification consumers, and dynamic group scopes and atomic detach/cancel logic were verified on PostgreSQL.
23. At Stage 10 closing, the AI isolated the maintenance gate as a pure decision rule (`CANCEL`, `DEFER`, `PROCEED`) before introducing full SMTP delivery. Time boundaries, overlapping windows, process restarts, and active probe continuity during maintenance were proven via acceptance tests.
24. In Stage 11 architecture, the AI evaluated existing schema, OpenAPI, auth queues, and outbox models against notification delivery requirements. Gaps in default policy creation, recipient token delivery, and post-materialization maintenance races were identified. The design resolved these via Revision 16, token queue reuse, snapshotted DOWN/RECOVERY lineage, claim-time maintenance rechecks, and a strict no-retry policy on ambiguous SMTP outcomes.
25. In Stage 11 Slice 1, the AI implemented Revision 16 with policy reconciliation, recipient transactional email lineage, narrow SECURITY DEFINER functions, public recipient confirmation, and incident delivery evidence schemas. An issue where demo seeds collided with default policy triggers was resolved prior to deployment.
26. In Stage 11 Slice 2, the AI expanded generated OpenAPI contracts to 58 operations, authored owner-scoped recipient/policy services, and connected the encrypted verification queue. SQL type mismatches were resolved with explicit casts. Token rotation mechanics were hardened so un-claimed verification tasks cancel safely without falsely showing in-flight SMTP operations as cancelled.
27. At Stage 11 closing, the AI verified two-worker delivery claims, post-materialization maintenance suppression, restart-safe deferred recoveries, and terminal handling of ambiguous SMTP outcomes on PostgreSQL. Real Mailpit acceptance confirmed recipient verification and operational HTML/text email templates.
28. In Stage 12 architecture, the AI audited partitioning, rollups, health intervals, and scheduler tables against retention goals. A foreign-key chain tying raw runs to queue rows and incidents had rendered 30/90/400-day purges impossible. The architecture resolved this via compact run evidence, insert-time lineage validation, cursor indexes, deterministic rollup windows, and an isolated housekeeping runtime.
29. In Stage 12 Slice 1, the AI verified data upgrades from Revision 20 to Revision 21 on real fixtures, confirming that decoupled run evidence enabled independent queue and raw run purging. Aggregations were aligned to source resolutions, and time coverage invariants were enforced.
30. In Stage 12 Slice 2, the AI built the housekeeping worker featuring four bounded loops and restricted SECURITY DEFINER functions. Dual-replica testing exposed potential unique constraint contention during concurrent rollup rebuilds; this was mitigated without touching past migrations by introducing a forward-only advisory lock lane.
31. In Stage 12 Slice 3, the AI implemented private history and incident APIs matching canonical OpenAPI contracts. The API role was restricted from directly scanning housekeeping rebuild tables, instead consuming owner-scoped projection horizons via narrow security functions. Tombstones, cross-tenant 404s, signed pagination cursors, and incident gap synthesis were validated on PostgreSQL.
32. At Stage 12 closing, the AI established an isolated history capacity test harness. Benchmarks confirmed query execution times under housekeeper load, verifying partition pruning across 420,000 rollup rows (equivalent to 50.4 million raw samples) well within latency targets.
33. In Stage 13 architecture, the AI addressed multi-replica API event delivery, EventSource heartbeat visibility limitations, and race conditions between REST snapshots and SSE streams. The design established a dedicated realtime relay, PostgreSQL transactional wake-ups, local owner hubs, a custom fetch-stream client, and snapshot reconciliation.
34. In Stage 13 Slice 1, the AI authored Revision 27 with minimal service roles and built the standalone realtime worker process. Real PostgreSQL tests verified commit/rollback notification atomicity, payload redaction, and fence recovery.
35. In Stage 13 Slice 2, the AI built the private SSE endpoint on a dedicated PostgreSQL connection listener separate from request pools, backed by bounded client hubs and RLS-scoped projections. Broadcast correctness, multi-replica isolation, listener auto-reconnects, and slow-consumer eviction were validated.
36. In Stage 13 Slice 3, the AI connected the zero-dependency fetch-stream parser, reconnection state machines, and stream-before-snapshot buffering to the React frontend, completing the `REALTIME` cutover with Revision 28. CORS header issues with hijacked raw streams were diagnosed and corrected, passing full multi-browser Playwright acceptance tests.
37. At Stage 14 start, the user requested direct UI implementation without a separate frontend architecture document. The AI leveraged existing realtime and status contracts to build live status summaries, operational filters, freshness indicators, and real-time incident counters into the responsive React dashboard, protected by component and Playwright acceptance suites.

## Security and Confidentiality

Live passwords, session cookies, CSRF tokens, single-use credentials, encryption keys, and third-party credentials are never committed to version control or recorded in these logs. Accounts and Mailpit messages generated during testing are mock development artifacts; submission evidence contains no secrets.
